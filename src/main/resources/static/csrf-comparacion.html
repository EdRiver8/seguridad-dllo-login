🛡️ Demostración: ¿Por qué JWT protege contra CSRF?

Esta página simula un ataque CSRF desde un sitio malicioso intentando eliminar usuarios en tu aplicación.

❌ VULNERABLE

🔓 Basic Auth

Problema: Las credenciales se envían automáticamente con cada request.

Ataque: El navegador incluye el header Authorization aunque la petición venga de otro sitio.

⚠️ Este ataque FUNCIONARÁ si has hecho login con Basic Auth

✅ PROTEGIDO

🔒 JWT Token

Protección: El token JWT NO se envía automáticamente.

Bloqueo: El atacante no tiene acceso al token (está en localStorage de otro dominio).

✅ Este ataque FALLARÁ porque no tenemos el token JWT

📊 Consola de Ataques

🎓 Explicación Técnica

❌ Por qué Basic Auth es vulnerable a CSRF:

  • El navegador almacena credenciales en su cache de autenticación
  • Al hacer un request, el navegador incluye automáticamente el header Authorization: Basic ...
  • Un sitio malicioso puede hacer requests y el navegador incluirá las credenciales

✅ Por qué JWT NO es vulnerable a CSRF:

  • El token JWT se guarda en localStorage o sessionStorage
  • JavaScript de otro dominio NO puede acceder a ese storage
  • El token debe ser incluido manualmente en cada request
  • Un sitio malicioso no tiene el token, así que no puede hacer el request

🔑 Solución implementada:

  • ✅ JWT para autenticación (stateless, seguro contra CSRF)
  • ✅ Tokens con expiración (24 horas)
  • ✅ Claims personalizados (rol, userId)
  • ✅ Filtro JWT que valida en cada request
